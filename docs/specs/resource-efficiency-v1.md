# Resource efficiency v1

## Outcome and design comparison

Implement the first development slice of the November 13 resource review:
measure avoided inference before adding infrastructure, and prepare one existing
ordinary notebook for a browser evaluation. This is development authorization,
not authorization to spend the experimental ceiling or provision services.

Today the selected classroom supports AI-off, explicit saved-file submission,
bounded selected-code capture and deterministic completeness checks. Portage
already owns admission, routing and accounting. Its newer OpenRouter instructor
walkthrough is separate work; this change does not replace or edit it.

Add an offline E1 planner/importer here because the comparison spans tutoring,
source questions, drafts and ordinary data work. Reusing Portage's coding-ladder
score would conflate distinct success criteria. The harness sends no requests,
executes no notebooks, and cannot qualify an endpoint. Import each actual
Portage attempt, including failures/unknown usage, when a separately authorized
experiment exists. No new scheduler, identity authority, model route or retry.

Extend Waypoint's explicit assignment profiles with a learner-only bundle and
advisory compatibility report. Reuse its public NHANES starter and deterministic
submission contract. Do not bundle operator solutions or claim source inspection
establishes browser execution, persistence, network privacy or submission.

## Finite implementation plan

1. Freeze 24 authored synthetic tasks (six per E1 class), review criteria and
   ordinary alternatives; create a deterministic randomized baseline/candidate
   schedule on identical endpoint/model/runtime pins. Unconfigured approval
   remains visible as execution unavailable.
2. Import a plan-bound attempt journal and human judgments. Enforce complete
   workflow coverage, unique attempts, usage/cost/time accounting, all E1 ceilings,
   and explicit zero-call save/reopen/export evidence. Missing evidence cannot
   pass; fixture evidence cannot become measured quality or endpoint acceptance.
3. In a separate Waypoint branch, package only reviewed learner paths with byte
   digests and a named hosted fallback. Preserve the current runtime and presenter.
4. Verify failure cases and existing affected checks; record exact pins and
   remaining institutional/browser/endpoint gates here.

## E1 SPDX inventory pilot, 13 November 2026

The existing builder produces an allowlisted, deterministic ZIP with an
internal SHA-256 manifest. The pilot extends the CLI to emit an SPDX JSON
sidecar for that exact ZIP and lists both artifacts in `SHA256SUMS`. The
existing ZIP layout, manifest schema, and source allowlist still define the
distribution. The sidecar includes the generated manifest as a ZIP member
and carries no copies of the catalog or other source content.

[SPDX 2.3](https://github.com/spdx/spdx-spec/releases/tag/v2.3) provides the
package, file, checksum, relationship, and license fields needed here. The
[SPDX Python validator](https://pypi.org/project/spdx-tools/0.8.5/) supports
SPDX 2.2 and 2.3. This pilot records SHA-256 file checksums alongside the
required SHA-1. [SPDX 3.0.1](https://spdx.github.io/spdx-spec/v3.0.1/serializations/)
uses JSON-LD with schema and semantic validation, and the selected tool has
experimental write-only support for 3.0. Dataset and AI profiles would need
their own inputs and review. This pilot covers only the E1 source archive.

Source evidence comes from the archive bytes, its Git revision, and the
Python files' existing SPDX headers and scoped license notice. The aggregate
license, unreviewed file licenses, and dependency inventory use `NOASSERTION`.
The external Python requirement is documented. The sidecar does not assess
redistribution rights or verify the availability, terms, or licenses of
referenced notebooks, datasets, or services.
