# Build-Ready Reference: Open-Source, Local-First Personal AI Routing Stack (July 2026)

> Saved from chat per MANIFEST.md; canonical staging name `routing-stack-reference.md`.
> Evidence base for `herdr-build-plan.md` — the pitfall register reads against §1 here.

## TL;DR
- **Build ~85% of "Herdr" out of off-the-shelf, known-good components and write only the thin policy/verifier/learning glue you already scoped.** LiteLLM proxy already ships the router strategies, health-checked multi-deployment load balancing, per-key/tag budgets, provider fallbacks, and prompt-cache passthrough you planned; OpenRouter already ships session-pinned cache-affinity routing. The genuinely custom code is small: Herdr's task-classification/effort-selection policy, `failup.py`, `measure.py`, and `distill.py`.
- **For the routing "brain," start with statistical per-task-class priors (a table of pass-rates per tier), not ML.** The published research that best matches your verifier-verdict signal — contextual-bandit routers learning from binary success/failure (PILOT, BaRP, OrcaRouter) and closed-loop escalation-driven distillation (RouteNLP) — validates your design but ships mostly as papers, not adoptable repos. RouteLLM is the one drop-in router repo, but it is preference-trained and binary, so adapt its serving harness rather than its training method.
- **The single biggest documented risk to your learning loop is "routing collapse": a self-labeled, cheapest-first dataset is heavily skewed toward "cheapest-tier-optimal," and a naïve classifier trained on it collapses to always predicting the cheap tier.** Mitigate with class-weighted/cost-sensitive objectives, verifier grounding (never an LLM judge alone), and a domain pre-filter — details in Details §5.

## Key Findings
1. **LiteLLM is the correct gateway and covers most of your requirements natively.** Use `model_name` aliases as capability groups; list the same alias twice (once per Ollama endpoint) for health-checked load balancing; use `routing_strategy`, `order`-based priority, cooldowns, and `fallbacks` for the ladder; `/key/generate` with `max_budget`/`budget_duration` and tag budgets for spend caps; and `cache_control_injection_points` for prompt-cache passthrough. Split config with the `include:` directive to generate from a single registry.
2. **Ollama-through-LiteLLM tool-calling and streaming are the top pitfalls.** Multiple 2026 bug reports show tool calls returned as raw JSON, `stream_chunk_builder` dropping tool calls (Ollama omits tool-call IDs), and `JSONDecodeError` on truncated tool arguments. Use the `ollama_chat/` provider prefix (not `ollama/`), pin a known-good LiteLLM version, and test tool-calling end-to-end per model.
3. **Frontend wiring is well-trodden.** Aider points at the proxy with `--openai-api-base`/`--openai-api-key` and a `.aider.model.metadata.json` (fully-qualified `provider/model` keys). OpenHands uses LiteLLM natively but requires the doubly-prefixed slug (`openrouter/vendor/model`) and supports headless automation. Open WebUI connects as an OpenAI connection and has built-in SearXNG web search + RAG.
4. **Cache-affinity routing largely exists in OpenRouter already** via account/model/conversation sticky routing, overridable with an explicit `session_id`. The critical trap: specifying `provider.order` disables sticky routing (mutually exclusive). Groq (Kimi K2 family, GPT-OSS) and DeepSeek cache automatically; Anthropic needs explicit `cache_control` breakpoints.
5. **The routing research most compatible with a verifier-verdict signal is the contextual-bandit / cascade-with-verification family**, not preference-based routers. Adopt cascade-with-verification (FrugalGPT/AutoMix/ABC), a LinUCB-style bandit for online adaptation, and conformal thresholds — but expect to write the integration yourself; open reference code is thin outside RouteLLM and the ABC repo.
6. **Memory: one embedded store (Chroma or LanceDB) + one Ollama embedding model is the least-friction option**; Qdrant if you want payload filtering and the cleanest MCP memory server. Open WebUI's built-in RAG is fine standalone but not shared across Aider/OpenHands.
7. **Budget/rescue gating is a solved primitive in LiteLLM**: hard `max_budget` per virtual key + `budget_duration`, model-specific budgets, and budget windows. The confirm-gate, verified-failure requirement, and audit log are custom (small) Herdr logic.

## Details

### 1. LiteLLM gateway — best-practice config (2026)

**Deployment.** Use the official Docker image `ghcr.io/berriai/litellm` and prefer the `-stable` tag (LiteLLM states stable images undergo a 12-hour load test before publishing). Recent releases are on the v1.93.x line (v1.93.0 shipped fixes such as honoring `cache_control` TTL on Bedrock cachePoint blocks). Pin an exact stable tag and upgrade deliberately. Enable a Postgres DB (`STORE_MODEL_IN_DB`) so budgets, virtual keys, and spend logs persist; tag budgets specifically require Postgres.

**Model aliases / capability groups.** The `model_name` field is the user-facing alias; multiple entries can share one alias to form a load-balanced group. Use `model_group_alias` to remap names, and attach arbitrary `model_info` fields (tier, capabilities, context_window) for Herdr to read via `/model/info` (note: custom `model_info` is NOT exposed on the OpenAI-compatible `GET /v1/models` to key holders — read it admin-side).

**Two Ollama endpoints with health checks + load balancing.** List the local tier twice under one alias (`qwen3-coder-local`), one entry per Mac's Ollama endpoint, with `order` to prioritize the always-on iMac and the MacBook as `order: 2`. Set `routing_strategy` (`simple-shuffle` default; `least-busy` or `latency-based-routing` are options). Enable **health-check-driven routing**: a background loop pings each deployment on an interval and proactively removes unhealthy ones from the pool before a user request lands; tune `allowed_fails_policy` to avoid false positives from transient noise. Cooldowns temporarily eject failing deployments. For a two-Mac single-user setup you can skip Redis (Redis is for multi-proxy-instance shared state).

**Budget enforcement / spend tracking.** Create virtual keys with `max_budget` + `budget_duration` (e.g., 30d); layer **budget windows** (`budget_limits: [{budget_duration: 24h, max_budget: X}, {budget_duration: 30d, max_budget: 10}]`) to catch a runaway day inside a monthly ceiling. Use **model-specific budgets** (`model_max_budget`) to hard-cap the Opus rescue at $10/month independent of other spend, and **tag budgets** to track spend per frontend (aider/openhands/openwebui). `budget_fallbacks` can silently reroute an over-budget model to a cheaper one — useful, but for the rescue path you want a *hard block*, not a silent fallback, so keep the Opus key's `model_max_budget` as a wall.

**Provider fallbacks / the ladder.** Use `fallbacks` (model-group level) and `order` (within a group) to encode: local → Groq → OpenRouter → (gated) Opus. When an `order=1` deployment fails, the router tries `order=2`, each level getting its own retries. Note LiteLLM v1.92.x introduced beta "autorouter"/routing plugins — treat as beta.

**Prompt-caching passthrough.** LiteLLM supports `cache_control_injection_points` in model config to inject `cache_control` at specified message positions, and an auto-inject flag for Anthropic/Bedrock (default 5-min ephemeral; `LITELLM_ANTHROPIC_PROMPT_CACHING_TTL` for 1h). It stands down if the client already supplies `cache_control` (client checkpoints win) and respects the 4-block provider limit. This is provider-side caching (no Redis), distinct from LiteLLM's own response cache.

**Generate config from one registry.** Use the `include:` directive to compose `config.yaml` from external YAML files (`include: [model_config.yaml]`). Best practice: keep a single source-of-truth registry (YAML/JSON) and render `model_list` + `model_info` from it in your build step. Reference secrets with `os.environ/VAR` (a known footgun: env substitution has caused "no model_name" errors when the var isn't actually present at proxy load — validate env at startup).

**Pitfalls with Ollama backends.** Documented 2026 issues: (a) tool/function calls returned as raw JSON in message content instead of structured `tool_calls` (Issue #19742) — works direct-to-Ollama and via OpenRouter but broke through LiteLLM; (b) `stream_chunk_builder` drops Ollama tool calls because Ollama doesn't return tool-call IDs (PR #11171/#11528 add IDs); (c) `JSONDecodeError: Unterminated string` when tool arguments are truncated (Issue #25985). Guidance: use the `ollama_chat/` route (better chat/tool handling than `ollama/`), require LiteLLM ≥ the version that fixed streaming tool-call IDs, disable streaming for tool-heavy flows if you hit reconstruction bugs, and add a per-model tool-calling smoke test to your CI.

### 2. Frontend wiring (least friction)

**(a) Aider → LiteLLM.** Launch with `aider --openai-api-base http://0.0.0.0:4000 --openai-api-key <virtual-key>` and set `--model openai/<alias>` so LiteLLM routes via the OpenAI-compatible path. For models Aider/LiteLLM don't know, add `.aider.model.metadata.json` with a fully-qualified key (`"deepseek/deepseek-chat": {max_input_tokens, input_cost_per_token, litellm_provider, mode}`) — the `provider/` prefix must match `litellm_provider`. Override behavior via `.aider.model.settings.yml` (`edit_format`, `use_repo_map`, `extra_params.extra_headers`, `cache_control: true`, `caches_by_default`). Prompt caching: run with `--cache-prompts` (caches system prompt, repo map, read-only files, editable files) and `--cache-keepalive-pings` to keep the 5-min Anthropic cache warm; caching stats/costs are unavailable while streaming (use `--no-stream` to see them). Git workflow: Aider auto-commits each change; use `--map-refresh` to control repo-map recomputation in large repos.

**(b) OpenHands → LiteLLM/OpenRouter with local models.** OpenHands uses LiteLLM as its abstraction layer. Set the LLM model to the full LiteLLM slug and point base URL at the proxy. **Critical slug pitfall:** with OpenRouter the slug is doubly-prefixed `openrouter/<vendor>/<model>` (e.g., `openrouter/anthropic/claude-sonnet-4.5`); native Anthropic uses a hyphen (`anthropic/claude-sonnet-4-5`). A documented bug (#13049) shows an external LiteLLM proxy stripping the provider prefix — verify the model string arrives intact. For headless automation: `openhands --headless --json --override-with-envs --exit-without-confirmation -t '<task>'` with `LLM_MODEL`/`LLM_API_KEY`/`LLM_BASE_URL` envs; `OPENHANDS_SUPPRESS_BANNER=1` keeps JSON clean. **Install pin:** the current CLI is `uv tool install openhands --python 3.12`; `pip install openhands-ai` is the legacy V0 SDK (wrong package). **macOS Docker runtime:** mount code via `SANDBOX_VOLUMES=/path:/workspace:rw`, set `SANDBOX_USER_ID=$(id -u)` to avoid root-owned files, add `extra_hosts: host.docker.internal:host-gateway`, mount `/var/run/docker.sock`, persist `~/.openhands`, and set `SANDBOX_RUNTIME_CONTAINER_IMAGE` to the matching `-nikolaik` runtime tag. To reach Ollama on the Mac host from inside the container, use `host.docker.internal`. Note community reports of OpenHands being unreliable with some local Ollama models (stalling) — validate your specific local model, or route OpenHands to the hosted-open tier for autonomy-heavy tasks.

**(c) Open WebUI → LiteLLM.** Add LiteLLM as an OpenAI connection (Admin → Settings → Connections → OpenAI; base URL `http://litellm:4000/v1`, the virtual key). RAG uses the same OpenAI-compatible endpoint for embeddings — expose an embedding model in LiteLLM and Open WebUI's vector search works unmodified. **SearXNG web search:** run SearXNG (Docker), set `ENABLE_RAG_WEB_SEARCH=True` (newer builds: `RAG_WEB_SEARCH_ENGINE=searxng` / web-search toggle), and `SEARXNG_QUERY_URL=http://searxng:8080/search?q=<query>` using the internal Docker network name. SearXNG must return JSON format for Open WebUI. Common breakage: version mismatches between Open WebUI RAG env var names across releases, and pointing `SEARXNG_QUERY_URL` at localhost instead of the container name. Pin the Open WebUI image (`ghcr.io/open-webui/open-webui:main` moves fast — pin a dated/versioned tag) and pin the LiteLLM image; a typo in `litellm-config.yaml` takes down model access for all frontends.

### 3. Cache-affinity routing

**The problem is real and quantified:** Kimi K2 on Groq is billed at **$1.00/M input uncached vs $0.50/M cached input (and $3.00/M output)**, per Groq's official pricing and its blog "Introducing Prompt Caching on GroqCloud," which states caching delivers "a 50% cost savings on cached tokens... with no code changes required." Caching first rolled out on `moonshotai/kimi-k2-instruct`, then Kimi K2-0905, which Groq calls "The largest context window of any model on GroqCloud to date" at 256k. Anthropic reads cost 0.1× base input (90% off) but writes cost 1.25× (5-min TTL) or 2× (1-h TTL); per Anthropic's docs the economics "pay off after just one cache read on the 5-minute tier, and after two reads on the 1-hour tier." DeepSeek and OpenAI cache automatically (implicit); Anthropic, Alibaba/Qwen, and MiniMax require explicit `cache_control` breakpoints.

**What already exists (adopt, don't build):** OpenRouter implements **sticky provider routing**: subsequent requests from the same conversation are pinned to the provider that last served them (when that provider's cache-read price beats a cold prompt). Granularity is account × model × conversation; by default OpenRouter hashes the first system message + first non-system message to identify a conversation. **You can pass an explicit `session_id`** to use as the sticky key directly — the right primitive for Herdr to pin a task/session. **Hard trap: specifying `provider.order` disables sticky routing entirely (the docs state they are mutually exclusive).** So a cache-affinity design and a manual provider-ordering design conflict on OpenRouter — pick session_id-based stickiness for cache-sensitive high-frequency flows (Kimi terminal edits) and reserve explicit ordering for correctness-critical routes.

**Provider cache primitives you need for the cost model:**
- **Anthropic:** explicit `cache_control` breakpoints (max 4); 5-min default TTL refreshed free on hit; 1-h TTL via `ttl: "1h"`; writes 1.25×/2×, reads 0.10×; min cacheable prefix is model-dependent (Opus 4.8 = 1,024 tokens, Haiku 4.5 = 4,096). Cached reads (`cache_read_input_tokens`) are excluded from ITPM rate limits. Invalidation gotchas: whitespace changes, reordered tool definitions, system content type mismatch (string vs typed array), TTL elapse.
- **Groq:** automatic, no code change, 50% cached-token discount, cached tokens don't count toward GroqCloud rate limits; available on Kimi K2 family and GPT-OSS 20B/120B.
- **DeepSeek:** automatic/implicit; construction is best-effort and can take seconds (an immediate follow-up may still show `cached_tokens: 0`).
- **OpenRouter:** passes through provider caching; automatic top-level `cache_control` supported on Anthropic/Vertex/Azure/Claude-on-AWS. **`prompt_cache_ttl` at the top level is silently ignored by OpenRouter** (empirically verified in the opencode issue thread) — set TTL via the `cache_control` object on Chat Completions/Anthropic Messages, not a top-level field.

**Effective-cost model to implement in Herdr:** for each candidate model compute `effective_input_cost = p_hit · cache_read_price + (1 − p_hit) · (cold_price + write_premium_if_first)`, where `p_hit` is estimated from your sticky-window state (session age vs TTL, whether the stable prefix is byte-identical). Keep a sticky window per task-session: while within TTL and the prefix is stable, pin to the same provider/model even if a nominally cheaper cold model exists, because a cold switch pays the full uncached rate plus a write premium. This is the "cache-state-aware cost" primitive; there is no turnkey open implementation, but the OpenRouter `session_id` + provider docs above give you all the mechanics.

### 4. Published routing / cascade research to build on

**Taxonomy.** Two families: (a) **cascades** (run cheap→expensive sequentially, exit early when a decision module is confident) and (b) **routers** (a predictive model picks one model up front). Your ladder is a cascade with a verifier as the deferral rule.

- **RouteLLM (Ong et al., LMSYS, 2024; ICLR 2025; repo `lm-sys/routellm`).** The one true drop-in: OpenAI-compatible server, pretrained routers (matrix-factorization `mf`, BERT, causal-LLM classifiers), `--strong-model`/`--weak-model` flags. Per the LMSYS blog, its routers achieve "cost reductions of over 85% on MT Bench, 45% on MMLU, and 35% on GSM8K as compared to using only GPT-4, while still achieving 95% of GPT-4's performance" — the matrix-factorization router reaches 95% GPT-4 quality using only ~26% GPT-4 calls (14% with LLM-judge augmentation). Limitations for you: it's **binary** (strong vs weak) and **preference-trained** (Chatbot Arena win-rate), not verifier-trained, and it routes up-front rather than cascading. **Adopt its serving/eval harness; replace `calculate_strong_win_rate` with your own per-task-class prior computed from verifier verdicts.**
- **FrugalGPT (Chen et al., 2023).** Foundational cascade: prompt adaptation + LLM approximation (caching) + LLM cascade with a DistilBERT scorer `g(q,a)`. Needs ~500 training samples per tier scorer. Portkey and others have open reimplementations of the pattern. Directly maps to your `failup.py`/effort ladder — but replace its learned scorer with your deterministic verifier.
- **AutoMix (Aggarwal et al., NeurIPS 2024).** Few-shot self-verification + POMDP meta-router to decide escalate/accept; needs ≥50 samples per cascade step and runs self-verification ~8× at temp 1.0 (adds cost). Your deterministic verifier (tests/lint/diff/citation) is a cheaper, higher-precision substitute for AutoMix's self-verifier — same architecture, better signal.
- **Agreement-Based Cascading / ABC (Kolawole et al., TMLR 2024; repo `stevenkolawole/Agreement-Based-Cascading`).** Training-free deferral via ensemble agreement (voting); reports **2–25× cost reductions** and beats FrugalGPT/AutoMix without per-tier training. A working, adoptable Python cascade harness (Together.ai-based) you can study for tier/deferral structure.
- **Contextual-bandit routers that learn from binary success/failure (the closest match to your verifier-verdict signal):**
  - **PILOT (Panda et al., 2025)** — LinUCB with preference priors; routing as contextual bandit on **binary success/failure signals** (not full supervision); models budget as an online multi-choice knapsack. Directly compatible with verifier verdicts as the reward.
  - **BaRP / "Learning to Route LLMs from Bandit Feedback" (arXiv 2510.07429).** Multi-objective contextual bandit conditioned on a cost/quality trade-off vector; trains with policy gradient under bandit feedback (only the chosen model's outcome observed) — exactly your deployment reality.
  - **MixLLM (Wang et al., 2025)** — contextual bandit + policy gradient, domain-tagged query embeddings, online updates from binary feedback; reports **97.25% of GPT-4 quality at 24.18% of cost**.
  - **OrcaRouter (arXiv 2605.30736).** Production-oriented **LinUCB contextual bandit over lexical + sentence-embedding features (424-dim: 40 lexical + 384 embedding)**, one ridge regressor per arm, **hybrid offline warmup + optional online bandit updates** to only the selected arm. Ranked #2 on RouterArena (arena score 72.08, 75.54% accuracy at $1/1K queries) as of May 20 2026. **No open-source repo — it's a commercial product (orcarouter.ai)** — but its architecture is the reference blueprint for `measure.py` + online adaptation.
  - **RouteNLP (Guo, Wu & Yiu, arXiv 2604.23577; ACL 2026 Industry Track).** The single most on-point paper for your learning loop: a **closed-loop that clusters escalation failures, applies targeted distillation to cheaper models, and automatically retrains the router** — precisely your `distill.py`. Reports a financial-services pilot (~5K queries/day, 8 weeks): **58% inference-cost reduction, 91% response acceptance, p99 latency 1,847 ms → 387 ms**; and **40–85% cost reduction at 96–100% quality on structured tasks** across a six-task benchmark; targeted distillation gave **2× the cost improvement of untargeted (21.7% vs 9.4%)**. Only 25–35% of enterprise queries needed frontier models. No public code found. (Note: the widely-circulated "SLA violations under 3% with >50% cost reduction" phrasing is a third-party aggregator's paraphrase, not a verbatim paper claim — cite the 58%/91%/387ms pilot figures instead.)
- **Benchmarks to evaluate your router against:** RouterBench (405k inference outcomes), RouterArena (8,400 queries, 7 categories, automated leaderboard), LLMRouterBench (400k+ instances, 21 datasets, 33 models), RouterEval. Curated list: `MilkThink-Lab/Awesome-Routing-LLMs`.

**Which are directly compatible with a verifier-verdict signal vs preference labels:** PILOT, BaRP, MixLLM, OrcaRouter (bandit/binary-outcome) and FrugalGPT/AutoMix/ABC (cascade-with-verification) are compatible with pass/fail verdicts. RouteLLM and Hybrid-LLM are preference/label-trained — adopt their code/structure, not their training signal.

### 5. Learning-loop implementation

**Start simple, escalate deliberately:**
1. **Phase 1 — statistical priors (recommended start).** `measure.py` maintains a table: per (task-class × tier) → verified pass-rate, marginal cost, amortized cost per verified success. Router starts each task class at the cheapest tier whose historical pass-rate clears a threshold (e.g., ≥0.9). This is a Beta-Binomial / Thompson-style prior — no ML infra, fully interpretable, and matches your three-price accounting. Add a quality gate: a cost win is discarded if verified success rate drops.
2. **Phase 2 — contextual bandit (LinUCB / Thompson sampling)** once you have volume and want per-prompt (not just per-class) decisions. Features per the literature: **prompt/sentence embeddings + lexical features (length, code/math density) + task-class tag + historical pass-rate per tier** (this is exactly OrcaRouter's 40-lexical + 384-embedding recipe). Update only the chosen arm's parameters from the verifier reward. Optionally warm-start arms from Phase-1 priors (OrcaRouter's hybrid offline→online protocol).
3. **Phase 3 — targeted distillation (RouteNLP-style)** only at platform scale: cluster escalation failures, distill those cases into the cheaper local model, retrain the router.

**The dominant failure mode — routing collapse (design this out from day one).** The empirical study *"Unsolvability Ceiling in Multi-LLM Routing"* (Garg & Sagtani, arXiv 2605.07395, May 2026; 206,756 query-model pairs) shows that when the self-labeled dataset is skewed toward "cheapest-tier-optimal" (in their data **79.3% of solvable queries were optimal at the smallest tier**), a standard cross-entropy classifier **collapses to majority-class prediction — it predicts the cheap tier for essentially every query, ~0% recall on all other tiers.** They prove the collapse is caused by the *label marginal, not feature quality* (random features + shuffled labels reproduce it exactly), so better embeddings will NOT fix it. This is precisely the regime your cheapest-first, self-labeled loop creates. **Mitigations (adopt all):**
- Use **class-weighted / cost-sensitive objectives, focal loss, or minority oversampling** — never plain cross-entropy on the raw skewed labels. (Their balanced classifier recovered real per-tier recall: E2B 47.1%, E4B 13.3%, 26B 9.3%, 31B 54.8%.)
- Add a **domain/task pre-filter** that routes known-hard classes (e.g., certain agentic-coding or long-context tasks) to a stronger tier by default, rather than learning it from scratch (they saw a 40.4 pp exact-match routing gain on medical queries from such a pre-filter).
- **Ground labels in the verifier, never an LLM judge alone.** The same paper documents evaluation artifacts — LLM judges under-credit correct-but-terse answers and over-credit fluent-but-wrong ones, "directly suppressing the routing signal for larger tiers on the queries where routing provides the most value." Your deterministic verifier (tests/lint/diff/citation) is the right grounding; keep it deterministic.
- Watch **under-routing under distribution shift** (they saw router accuracy drop 39.5 pp OOD with under-routing errors dominating 621:1). A cheapest-first learner tends to strand hard queries at the cheap tier — your `ceiling_stall` failure class and fail-up guard are the correct countermeasure; make sure escalation actually fires.
- Track **Ceiling-Normalized Accuracy (CNA)** = (share of queries routed to a tier that solves them) / (share solvable by *any* tier), as a complement to raw cost savings, so you don't reward a router that's just cheap.

**Avoiding degenerate feedback loops generally:** hold out an exploration fraction (ε-greedy or Thompson) so the router keeps sampling higher tiers on task classes it has written off; recompute priors on a rolling window so model upgrades (new DeepSeek/Kimi/GLM versions) can re-open a class; and never let the model self-grade.

### 6. Memory layer

**Recommendation: one embedded vector store + one Ollama embedding model, shared via a thin service.** Ranked options:
- **Chroma (embedded) — lowest friction to start.** `pip install chromadb`, `PersistentClient(path=...)`, two lines to a working store; Apache-2.0; production-ready for small/medium corpora (millions of vectors on 4–8 GB). Best if you want minimal moving parts today.
- **LanceDB — best if ingestion/update churn is high.** Embedded, no server, columnar Lance format, multimodal, hybrid search. Caveat: multi-process concurrent access has limitations and the ecosystem is younger — relevant because Aider, OpenHands, and Open WebUI may hit it concurrently; front it with a single writer service.
- **Qdrant — best if you need payload filtering or the cleanest MCP memory server.** Rust, rich indexed metadata filtering, runs as one Docker container; community consensus (2026) is Qdrant for production RAG at scale, Chroma for prototyping. **Qdrant's MCP server is rated the cleanest "store-a-fact / retrieve-it" agent-memory server**; Chroma's MCP has the most collection-management tools; **Weaviate and LanceDB MCP servers are immature/archived as of 2026** — don't rely on them.

**Sharing across three tools:** the fewest-moving-parts pattern is a **single vector DB instance + one Ollama embedding model exposed through LiteLLM's `/embeddings`**, so Open WebUI RAG, and any Aider/OpenHands memory, all embed with the same model and write to the same store. **MCP is the 2026 cross-tool option:** run one Qdrant (or Chroma) MCP memory server and connect all MCP-capable frontends to it — this is the cleanest way to give Aider, OpenHands, and Open WebUI a *shared* memory rather than three silos. Open WebUI's built-in RAG (9 vector DB backends, hybrid BM25+vector, rerankers, SearXNG web search) is excellent **standalone** but is per-Open-WebUI, not shared — use it for chat/knowledge, and use the shared MCP/Qdrant store for cross-tool memory.

### 7. Budget / rescue gating

**Off-the-shelf (LiteLLM):**
- Hard cap the Opus rescue with a **dedicated virtual key** carrying `model_max_budget` for the Opus model = $10 and `budget_duration: 30d`; when spend crosses the cap LiteLLM rejects with a 429 `budget_exceeded` until reset. Do **not** attach `budget_fallbacks` to this key (that would silently reroute instead of hard-blocking).
- Add **budget windows** (24h + 30d) on the same key so a single runaway session can't burn the month in a day.
- Use **tag budgets** (per frontend) for observability and secondary caps.
- **Session budgets** (`max_budget_per_session` via `x-litellm-trace-id`/`session_id`) cap a single agent run — useful for OpenHands autonomy.
- Optionally set OpenRouter key-level credit limits as a second wall for the hosted-open tier.

**Custom (small, in Herdr / `failup.py`):**
- **Confirm-gate + verified-failure precondition:** the rescue path is only reachable after `failup.py` records a verified open-model failure (a verifier verdict, not a model's self-assessment), logs a machine-readable reason from your taxonomy (`unavailable`/`not_good_enough`/`policy_blocked`/`invalid_task`/`ceiling_stall`), and obtains explicit CLI confirmation. Implement as a wrapper that mints/authorizes the Opus key only when those three conditions hold.
- **Audit log:** LiteLLM spend logs + `/spend/logs` give you per-request cost attribution (tag/key/model); write Herdr's rescue-reason record alongside (task-class, failing tier, verifier output, confirmation timestamp) to your own append-only log for later `measure.py` analysis. (Full audit-log tooling is a LiteLLM Enterprise feature; for single-user, your own append-only JSONL is sufficient.)

### 8. Overall system shape — least-friction build order

**Build order (each step independently testable):**
1. **LiteLLM proxy + model registry.** Stand up the `-stable` Docker image with Postgres, one registry file rendered into `config.yaml` via `include:`. Define aliases/capability groups and both Ollama deployments with health checks. Verify `/v1/models`, streaming, and tool-calling per model (Ollama tool-calling is the known risk).

7. **Shared memory.** One Qdrant (or Chroma) + one Ollama embedding model via LiteLLM; optionally expose as an MCP memory server for cross-tool sharing.
8. **Learning loop hardening (`distill.py` + collapse guards).** Only after volume: class-weighted objectives, exploration fraction, rolling-window recompute, CNA tracking. Consider a bandit (LinUCB/Thompson) if per-class priors aren't granular enough.

**Where the ecosystem already ships what you planned to build (don't rebuild):**
- **Multi-endpoint load balancing + health checks + cooldowns + fallbacks** → LiteLLM router (not custom).
- **Per-key/tag/model hard budgets + windows + session budgets** → LiteLLM (not custom).

## Recommendations

**Stage 0 (this week):** Stand up LiteLLM `-stable` + Postgres + the two-Ollama load-balanced local tier with health checks; render config from one registry via `include:`. Gate: `/v1/models` lists everything, streaming works, and **tool-calling passes per model** (if Ollama tool-calling breaks through the proxy, use `ollama_chat/`, pin a fixed LiteLLM version, and disable streaming for tool flows).

**Stage 1:** Wire the three frontends with pinned versions and per-frontend virtual keys + tag budgets. Create the hard-capped ($10/30d, no `budget_fallbacks`) Opus rescue key and confirm the 429 fires.

**Stage 2:** Ship `failup.py` (deterministic verifier + taxonomy + ladder) and `measure.py` (priors + three-price accounting + quality gate). Router starts each task class at the cheapest tier with historical pass-rate ≥0.9. **Benchmark that changes the plan:** if verified success rate on any class drops after a cost-motivated downshift, revert that class's floor tier.

**Stage 3:** Add `session_id`-based cache-affinity for Kimi terminal-edit flows and the effective-cost model; do NOT set `provider.order` on those routes.

**Stage 4 (platform scale only):** Introduce the bandit (LinUCB/Thompson, OrcaRouter feature recipe) and RouteNLP-style targeted distillation — but only with the collapse guards (class-weighted objective, exploration fraction, CNA tracking). **Benchmark that changes the plan:** if the router's per-tier recall on non-cheapest tiers approaches zero (majority-class collapse), stop, rebalance labels, and keep the statistical-prior router instead.

**Thresholds to watch:** pass-rate floor per class (start 0.9); Opus monthly cap ($10, hard); cache hit-probability below which a cold cheaper model wins (compute from write-premium vs read-discount — for Anthropic 5-min, break-even is ≈1 read); CNA and per-tier recall to detect collapse.

## Caveats
- **Model/version specifics move fast.** DeepSeek V4 Flash, Kimi K2.7 Code, GLM-5.2, Opus versions and their exact cache prices/TTLs change frequently — verify each provider's current pricing/caching page before hard-coding the effective-cost model. Groq's automatic caching was confirmed for the Kimi K2 family and GPT-OSS 20B/120B; confirm coverage for any other hosted-open model you add.
- **OpenRouter `prompt_cache_ttl` top-level field is silently ignored** (empirically verified in third-party testing) — set TTL through `cache_control`, and test that cache reads actually register (`cached_tokens` > 0) rather than assuming.
- **RouteNLP, OrcaRouter, and the Unsolvability-Ceiling paper have no verified public code repos.** Treat them as design blueprints, not adoptable dependencies. RouteLLM and ABC are the routing repos with real code.
- **The "SLA <3% / >50% cost" RouteNLP figure is a secondary-source paraphrase**, not a verbatim paper claim; the primary pilot figures are 58% cost reduction / 91% acceptance / p99 387 ms.
- **Ollama tool-calling through LiteLLM has multiple open/recently-fixed bugs.** Don't assume it works — smoke-test it, and keep a fallback (hosted-open tool-calling via Groq/OpenRouter) for tool-heavy agentic runs if a local model's tool output can't be reconstructed.
- **OpenHands reliability with local Ollama models is mixed** in community reports; for autonomy-heavy tasks route it to the hosted-open tier and reserve local for cheaper, verifiable edits.
- **Single-user "Scale 1" lets you skip Redis and LiteLLM Enterprise features**; both become relevant (shared router state, audit-log tooling, multi-tenant budgets) when you scale into the education platform.
- **Some model names in the task (DeepSeek V4 Flash, Kimi K2.7 Code, GLM-5.2, Anthropic Opus current version) could not be independently price-verified in this research pass**; the caching mechanics and cost-model math are provider-general and hold regardless of the specific version, but plug in live per-token numbers before relying on the effective-cost formula for routing decisions.
